# FlatBook — практическая работа №2

Учебное веб-приложение сервиса бронирования квартир. Проект специально подготовлен для последующего размещения за Apache/Nginx с L4/L7-балансировкой, DNS-балансировкой и TLS-терминацией в следующей лабораторной работе.

## Что реализовано

- каталог квартир с фильтрацией по городу, датам и числу гостей;
- асинхронная загрузка каталога через `fetch`;
- асинхронное создание бронирования через `fetch`;
- PostgreSQL как общее хранилище данных для всех backend-экземпляров;
- защита от двойного бронирования одной квартиры на пересекающиеся даты на уровне PostgreSQL;
- `GET /api/node`, однозначно показывающий, какой backend обработал запрос;
- заголовок `X-Backend-Node` добавляется во все HTTP-ответы;
- `GET /healthz` для проверки backend и соединения с общей БД;
- два идентичных экземпляра приложения в `docker-compose.yml`: `backend-1` и `backend-2`;
- TLS/SSL в приложении отсутствует;
- пользовательские сессии не используются, следовательно нет локального session state в RAM/файлах.

## Соответствие ограничениям задания

### 1. Можно определить backend-узел

Эндпоинт:

```text
GET /api/node
```

Пример ответа первого экземпляра:

```json
{
  "backend_node": "backend-1",
  "hostname": "...",
  "time": "..."
}
```

Также каждый ответ содержит HTTP-заголовок:

```text
X-Backend-Node: backend-1
```

Имя текущего узла видно и в правом верхнем углу веб-интерфейса.

### 2. Хранилище не привязано к backend-ноде

Оба backend-экземпляра используют одну PostgreSQL через переменную `DATABASE_URL`. Данные не лежат на локальном диске `backend-1` или `backend-2`.

Поэтому сценарий отказа одной backend-ноды выглядит так:

1. Пользователь создаёт бронирование через `backend-1`.
2. Бронирование сохраняется в PostgreSQL.
3. `backend-1` выключается.
4. Запрос направляется на `backend-2`.
5. `backend-2` читает то же бронирование из общей PostgreSQL.

Это позволяет в будущей работе убрать отказавшую ноду из балансировки без потери прикладных данных.

> В рамках практической №2 PostgreSQL представлена одним сервисом. Отказоустойчивый кластер самой СУБД заданием не требуется; ключевое требование здесь — не связывать данные с конкретной backend-нодой.

### 3. Приложение не обрабатывает TLS/SSL

Go-сервер запускается обычным HTTP через `ListenAndServe`. Сертификаты, HTTPS-listener и TLS-конфигурация отсутствуют. TLS должен завершаться на Apache/Nginx в последующей работе.

### 4. Локальные пользовательские сессии отсутствуют

Приложение не создаёт HTTP-сессии и не хранит session state ни в RAM, ни в локальных файлах. Каждый запрос самодостаточен, а постоянные бизнес-данные находятся в PostgreSQL.

## Быстрый запуск

Нужны Docker и Docker Compose.

```bash
docker compose up --build
```

После запуска доступны два идентичных backend:

- `http://localhost:8081` — `backend-1`;
- `http://localhost:8082` — `backend-2`.

Оба используют одну базу данных.

Остановить:

```bash
docker compose down
```

Полностью удалить и данные БД:

```bash
docker compose down -v
```

## Что показать преподавателю

### Проверка двух узлов

```bash
curl http://localhost:8081/api/node
curl http://localhost:8082/api/node
```

В ответах будут разные `backend_node`: `backend-1` и `backend-2`.

### Проверка общего хранилища

Создать бронирование через первую ноду:

```bash
curl -X POST http://localhost:8081/api/bookings \
  -H "Content-Type: application/json" \
  -d '{
    "apartment_id": 1,
    "guest_name": "Иван Иванов",
    "email": "ivan@example.com",
    "check_in": "2026-10-10",
    "check_out": "2026-10-12",
    "guests": 2
  }'
```

Из ответа взять `id`, например `1`, и прочитать это же бронирование через вторую ноду:

```bash
curl http://localhost:8082/api/bookings/1
```

Это демонстрирует, что данные не зависят от конкретной backend-ноды.

### Проверка отказа backend-1

```bash
docker compose stop backend-1
```

После этого открыть:

```text
http://localhost:8082
```

Каталог и ранее созданные бронирования продолжат работать через `backend-2`.

Вернуть ноду:

```bash
docker compose start backend-1
```

## API

### `GET /api/node`

Идентификатор backend-ноды.

### `GET /healthz`

Проверка приложения и соединения с PostgreSQL.

### `GET /api/apartments`

Параметры запроса:

- `city` — город;
- `guests` — количество гостей;
- `check_in` — дата заезда `YYYY-MM-DD`;
- `check_out` — дата выезда `YYYY-MM-DD`.

Пример:

```text
/api/apartments?city=Москва&guests=2&check_in=2026-10-10&check_out=2026-10-12
```

### `POST /api/bookings`

Создание бронирования.

```json
{
  "apartment_id": 1,
  "guest_name": "Иван Иванов",
  "email": "ivan@example.com",
  "check_in": "2026-10-10",
  "check_out": "2026-10-12",
  "guests": 2
}
```

### `GET /api/bookings/{id}`

Получение созданного бронирования по ID. Используется в демонстрации общего хранилища между нодами.

## Почему двойное бронирование не пройдёт

В PostgreSQL на таблице `bookings` задано `EXCLUDE USING gist` для пары:

- `apartment_id`;
- диапазон `daterange(check_in, check_out, '[)')`.

Поэтому два backend могут одновременно получить запросы на одну квартиру, но база данных не позволит сохранить пересекающиеся даты. Это особенно важно при будущей балансировке запросов между несколькими экземплярами приложения.

## Переменные окружения

- `PORT` — HTTP-порт приложения, по умолчанию `8080`;
- `INSTANCE_ID` — идентификатор текущей ноды;
- `DATABASE_URL` — строка подключения к общей PostgreSQL.

## Что намеренно НЕ реализовано

- HTTPS/TLS в backend — запрещено условием, этим займётся Apache/Nginx;
- локальные session-файлы или session storage в памяти — запрещено условием;
- Nginx/Apache и балансировщик — относятся к последующей лабораторной №3, поэтому в практической №2 не включены в приложение;
- авторизация и аккаунты — не нужны для демонстрации требований данной работы и потребовали бы отдельной схемы сессий/токенов.
